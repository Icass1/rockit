# Next.js web refactor plan

Prepared 4 November 2026 against `61dce4c61`. Status: architecture proposal; application behavior has not been changed.

**Recommendation.** Refactor the web app around server-rendered initial content, explicit server/client boundaries, synchronously available translations, a semantic design system, and state ownership by purpose. Replace the `rockIt` application-wide service locator with scoped React providers and feature APIs. Preserve and isolate the playback engine while migrating its consumers. A single Context containing every piece of application state would work against the performance goal.

Server rendering removes the browser's “download JavaScript → hydrate → fetch → render” dependency for initial content. It still takes time to fetch and render on the server. The goal is useful, localized content in the first response, fewer requests, smaller payloads, and fast subsequent interactions. WebSockets, audio, pagination, searches, mutations, uploads, and offline storage will continue to make requests when needed.

**1. Review scope and evidence**

The complete static inventory covers 423 web source/configuration/test files and 48,469 lines, excluding public binary assets, generated Next.js files, dependencies, and `next-env.d.ts`. It includes all 34 App Router files, 256 component files, 59 `lib` files, 12 top-level hooks, 36 model files, 13 global stylesheet files, and nine test files. Feature stylesheets live in the component count. All files were scanned for imports, component boundaries, hooks, store subscriptions, HTTP calls, native controls, and color usage; findings below come from tracing the relevant source paths. The companion [file inventory](nextjs-refactor-inventory.md) records each file and its migration area. This is a source architecture assessment, not a claim that every interaction was exercised in a browser.

Shared dependencies reviewed include the HTTP transport and result model, DTO contracts, store wrappers, container registry, base user/queue/player classes, collection pagination/tree/geometry, recommendations, and environment configuration. Backend inspection covers session-cookie issuance, vocabulary resolution, generated HTTP code, and the contracts relevant to the proposed changes. This is not an audit of the entire backend or native mobile app.

The web manifest requests Next.js `^16.1.7`, React `19.2.3`, Tailwind v4, and Nanostores. Installed Next.js is `16.2.0`. Validate implementation against the lockfile and installed APIs; current online documentation can describe later 16.x features. Do not turn this refactor into an automatic upgrade to every latest release.

**2. Target architecture and ownership**

Keep FastAPI as the domain/API authority. Next.js owns web composition, rendering, navigation, and web-specific orchestration. Reuse generated DTO validation and the shared typed HTTP client rather than creating another API implementation.

| Kind of state                                  | Proposed owner                                                               | Examples                                                                         |
| ---------------------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Initial page content                           | Server route/data functions, passed as serializable props                    | Home sections, collection header, first rows, stats summary                      |
| Interactive API-backed data                    | TanStack Query, prefetched/hydrated by the server where initially visible    | Library pages, download browser, friends, notification pages, settings resources |
| Stable or infrequently changed cross-tree data | Small Context providers                                                      | Resolved vocabulary/locale, session snapshot, stable playback-runtime reference  |
| High-frequency runtime state                   | Existing narrow Nanostores subscriptions behind playback hooks               | Playback time, volume, queue position, transport/loading, synchronization        |
| Shareable navigation state                     | URL search parameters                                                        | Query, sort, media kind, stats range, download filters                           |
| Ephemeral UI state                             | Local React state/reducers, scoped Context where necessary                   | Dialog state, selection, input drafts, drag gesture state                        |
| Offline state                                  | Explicit browser persistence adapter                                         | Saved media, account-scoped snapshots, offline queue resolution                  |
| Domain rules                                   | Pure shared functions, feature services, playback classes, backend framework | Queue semantics, permission-dependent operations, provider orchestration         |

TanStack Query is a proposed new dependency for server data that remains interactive. It replaces custom loading/request-race/cache plumbing; it is not a requirement for static Server Component content. Do not add Redux/Zustand alongside Nanostores or a second query library. The important change is clear ownership, not choosing a fashionable store.

Context distributes values and stable services. It does not provide caching, request deduplication, cancellation, or selective high-frequency subscriptions by itself. React re-renders consumers when their Context value changes. Keep session, vocabulary, UI state, and runtime references in separate providers; never publish playback time through a broad application Context.

Server Components read request-scoped server functions, not client Context. A client provider may receive server-rendered children without turning those children into client modules. The provider must not import server page content itself. Pure card markup, headings, metadata, artwork, and layout stay server-renderable; interactive controls are client islands. Do not mark every primitive or an entire design-system barrel `"use client"`.

Proposed organization, keeping routes and the repository's model conventions:

```text
apps/web/
  app/                          Server layouts/pages; route errors/loading
  components/
    ui/                         Domain-free primitives
    layout/                     Shell and navigation composition
    media/                      Shared feature cards, rows, artwork, actions
    Home/, Library/, ...        Feature views and small client islands
    providers/                  Vocabulary, session, query, playback providers
  lib/
    api/server.ts               server-only BaseHttp adapter
    api/browser.ts              client-only BaseHttp adapter
    server/                     Request-local session and route loaders
    i18n/                       Shared translator factory and server resolver
    queries/                    Keys, options, mutation/invalidation rules
    playback/                   Browser runtime/adapters and service interfaces
    offline/                    Browser storage and offline entry point
    services/                   Pure/domain services without component state
  hooks/                        Focused UI/runtime hooks
  models/                       Web-specific contracts and types
  styles/
    globals.css                 Single global entry
    tokens.css                  Semantic palette and design tokens
    base.css                    Reset/document behavior
    animations.css              Shared motion and reduced-motion rules
```

Use unambiguous aliases: web `@/lib/*` must resolve to web code; shared imports use `@rockit/shared/*`. Currently TypeScript's shared-first alias resolution and webpack's web-first aliases disagree. Add real shared package subpath exports as needed, update shared imports/build configuration carefully, and check web and mobile. Remove the shared package's Next.js dependency if the confirmed lack of runtime imports holds through build validation.

**3. Server data, authentication, caching, and errors**

1. Split `lib/http.ts` into explicit server-only and browser-only adapters extending generated `BaseHttp`. The server adapter forwards only the current request's session cookie, uses `BACKEND_INTERNAL_URL` with the configured fallback, and defaults authenticated data to `cache: "no-store"`. The browser adapter retains `credentials: "include"`. Browser-only binary download/upload capabilities stay there. Preserve headers with `Headers`, rather than assuming every `HeadersInit` is a plain object.
   Thread optional cancellation/request options through generated endpoint methods where needed; having `signal` in the transport interface alone is insufficient if callers cannot supply it. Keep aborts distinct from user-visible network failures. Change the generator/template rather than patching its generated output.
2. Remove server imports of `rockIt`, browser storage, player classes, and browser service registries. Add boundary checks so an RSC import cannot accidentally pull them back in. Do not call Next Route Handlers from Server Components merely to reach FastAPI: that adds another HTTP hop.
3. Introduce `getSession()`/`requireSession()` with React `cache()` for request-local reuse. Reuse the validated session result across layout, route loader, metadata where relevant, and initial client provider. Avoid putting cookies or user headers into module-scoped mutable variables. Auth checks belong close to data access and mutations as well as layout; persistent layouts are not rechecked on every navigation.
4. Distinguish no session/expired session (redirect or login-required UI), forbidden (403), genuinely absent resource (404), invalid response, backend failure, and browser-offline mode. Handle redirects/not-found before generic catches. Never let an offline snapshot authorize a backend operation.
5. Fix `HttpResult` to retain its actual success/failure discriminator. Update the HTTP generator template when changing generated behavior (`apps/backend/core/utils/httpTemplate.txt`), regenerate, and test both malformed JSON and Zod-invalid bodies returned with HTTP 200. Keep source HTTP status available for diagnosis while treating validation failure as failure.
6. Share server loaders between metadata and route content using request memoization. Replace the unbounded module album cache with request-local memoization on the server and account-scoped query caching in the browser. Do not persistently cache authenticated album/playlist/provider responses merely because their identifiers are public UUIDs.
7. Run independent requests concurrently. Start optional work early, but do not make core HTML await slow external providers. Do not aggregate all application data into one giant root-layout bootstrap request.
8. Serialize plain DTO data, never managers, atoms, proxies, `HttpResult` instances, or credentials. Keep server-to-client props limited to what each view needs. Cap list payloads and avoid sending the same large queue on every card.
9. Use error boundaries for unexpected failures and retry with `reset()`. Make expected status decisions before the RSC boundary; production server errors may be sanitized. Add localized not-found/unavailable views, a root error fallback, and appropriate nested boundaries so a provider failure cannot blank the entire app.

Caching policy:

| Data                                                                      | Server policy                                                                            | Browser policy                                                       |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Session, private collections, home/stats, library, friends, subscriptions | No shared persistent cache; memoize within one render/request                            | Account/session-scoped query keys or props; clear on account changes |
| Vocabulary for authenticated user                                         | Request-local locale resolution; no cross-user reuse of `/vocabulary/user`               | Provider starts populated; explicit language replacement             |
| Public dictionary by language                                             | Explicit opt-in cache keyed by language and vocabulary revision                          | Versioned dictionary/offline fallback                                |
| Public provider metadata                                                  | Cache only after confirming permissions and public shape, with TTL and provider identity | Bounded query cache; retain provider cooldown/rate-limit behavior    |
| Images/static assets                                                      | Existing appropriate immutable/image caching                                             | Worker/image cache                                                   |
| Audio/video                                                               | Direct media URLs and existing range behavior                                            | Explicit offline saved media; do not cache arbitrary partial streams |

Do not enable Cache Components or static rendering for personalized routes just to claim modern Next.js usage. Start with dynamic authenticated rendering and explicit caches. Evaluate advanced caching only against supported installed APIs and measured benefit.

**4. Vocabulary available on the first render**

The fix is to make dictionary availability a render input, rather than an effect that mutates a global atom.

1. Create a pure typed translator factory usable on the server and client, retaining backend vocabulary keys and interpolation rules. Server vocabulary loading returns plain `VocabularyResponse` data. Client `VocabularyProvider` initializes synchronously from that data; `useVocabulary()` reads it directly.
2. For protected pages, resolve the user's dictionary server-side alongside the session check. For login/register, resolve an explicit language preference cookie, then normalized `Accept-Language`, then English. Restrict preference values to supported languages. Use the endpoint's resolved `currentLang`, including its existing English fallback.
3. Set document `lang` and direction from the resolved initial locale; root currently hardcodes `lang="en"`. Consider Arabic direction deliberately, including icons and directional layouts. Keep HTML locale, dictionary, formatting, and provider snapshot consistent.
4. Use a generated English fallback dictionary sourced from backend vocabulary definitions, checked for key completeness. Do not hand-maintain another set of English UI strings. If backend vocabulary is unavailable, render a complete fallback or an intentional localized unavailable state; never an empty dictionary that exposes keys.
5. Migrate every visible string, including tooltips, accessible names, validation/errors, chart labels, offline view, auth pages, menu items, and metadata fallbacks. Remove ad hoc `value || English` and `value !== key` workarounds. Missing-key diagnostics belong in development/checks; production displays a translated fallback.
6. Language changes update the backend preference, fetch/validate the complete replacement dictionary, then atomically publish dictionary and locale. Refresh the server route to update server-rendered text, coordinate navigation/pending state, and persist the preference cookie through a supported mutation path. Keep the old complete dictionary while the replacement is pending. Avoid duplicated success toasts.
7. Temporarily expose a vocabulary-manager compatibility adapter for shared playback notifications. The adapter reads the current provider-owned translator; it never starts a second vocabulary request. Remove legacy UI vocabulary atom subscriptions as consumers migrate. Inject the translator into the runtime instead of writing a server-side global atom.
8. Offline vocabulary loads only in the offline application entry, keyed by locale/version and the selected account context where needed. It must not overwrite a newer online server snapshot after hydration.

**Acceptance:** with JavaScript disabled, delayed, or CPU-throttled, server HTML contains translated headings/navigation/forms; no known translation keys appear as UI text. The first client render matches it. Login, register, not-found, errors, language switching, and offline entry satisfy the same contract.

**5. Persistent shell and client runtime**

Replace `AppClientLayout` with a server-composed shell plus narrowly scoped client providers. Keep the persistent playback provider inside the authenticated layout and outside changing pages, so navigation and `router.refresh()` do not recreate audio elements or stop playback.

Construct a side-effect-free runtime per mounted application instance. Context provides a stable runtime reference. Start sockets, listeners, persistence, media session, and synchronization in an explicit lifecycle, with idempotent `start()`/`stop()`/`dispose()`. Constructors and provider render must not start I/O. Preserve browser user-gesture requirements for audio activation. Test Strict Mode setup/cleanup/setup, Fast Refresh, logout, and account replacement; guard work with a session generation so late responses cannot restore the old user.

Seed the user and relevant queue snapshot before first render. Fetch a bounded initial queue window once where the player needs it; never the whole library/queue in every route. WebSocket state reconciles after connection and retains playback ownership and playback-ID protections. Do not let a stale hydration snapshot reset a playing track. Connect immediately on the first attempt; apply backoff only after failures. Bind message handlers before connecting, then reconcile changes that occurred between server render and subscription. If the protocol lacks a revision, use an explicit post-connect resync of the affected state.

Keep shell content independent of socket readiness. Navigation labels and the user menu should not wait for `sessionReady` or mount flags when the server already supplied that data. Browser-only features can keep stable placeholders where no meaningful server snapshot exists. Remove broad `suppressHydrationWarning` and client-only rendering workarounds once deterministic snapshots exist; retaining a justified browser-only island is valid.

Load heavy dialogs, upload editors, PiP, full lyrics/queue panels, charts, map, and administrative tab content when needed. CSS hiding desktop/mobile markup does not prevent code loading or mounting effects. Mount expensive device-specific interfaces deliberately after stable initial rendering, without changing the custom desktop breakpoint or briefly dropping the player.

**6. UI system and semantic Tailwind tokens**

Keep Rockit's dark identity and pink brand. Standardize appearance and interaction; this plan does not assume a separate visual redesign or automatic light theme.

Use one global CSS entry and Tailwind v4 `@theme inline` mappings. Store literal palette values only in the central token layer. Suggested roles:

| Role                   | Examples of generated utilities                                                   |
| ---------------------- | --------------------------------------------------------------------------------- |
| Page and text          | `bg-background`, `text-foreground`, `text-muted-foreground`                       |
| Surfaces               | `bg-surface`, `bg-surface-raised`, `bg-popover`, `text-popover-foreground`        |
| Main actions           | `bg-primary`, `text-primary`, `text-primary-foreground`                           |
| Secondary states       | `bg-secondary`, `bg-muted`, `bg-accent`, matching foreground roles                |
| Borders/focus/inputs   | `border-border`, `ring-ring`, `border-input`, `bg-input`                          |
| Feedback               | `bg-destructive`, `text-destructive`, `text-success`, `text-warning`, `text-info` |
| Media/chart decoration | `chart-1`…`chart-n`, `media-accent`, `media-accent-foreground`, `scrim`           |

`foreground` conventionally names readable foreground text; buttons should use an intentional pair such as `bg-primary text-primary-foreground`. Naming roles consistently matters more than replacing every existing gray with one gray. Check pink/foreground contrast, especially small labels on bright gradients.

Centralize spacing, typography, radius, shadows, control sizes, motion, z-index, shell offsets, safe-area values, and desktop media rules. Preserve `md` as width ≥768px **and** height ≥500px; share the matching media query with browser hooks. Replace manual page padding mutations with shell variables/scoped layout state. Maintain narrow screens, landscape, keyboard overlays, dynamic viewport heights, and scroll restoration in the custom scroll container.

Create `components/ui/` primitives with variants and sizes rather than per-feature color overrides:

| Group              | Components and behavior                                                                                        |
| ------------------ | -------------------------------------------------------------------------------------------------------------- |
| Actions            | Button, IconButton, LinkButton; variants, loading, disabled, focus, accessible icon names                      |
| Inputs             | Input, SearchInput, Textarea, Select, Field, Label, FieldError, helper text                                    |
| Choices            | Checkbox (including indeterminate), Switch, RadioGroup, ToggleGroup                                            |
| Ranges             | Slider and Progress; seek/volume variants, keyboard steps, drag lifecycle, live-stream/disabled state          |
| Overlays           | Dialog, AlertDialog, Popover, Tooltip, DropdownMenu, ContextMenu, Sheet                                        |
| Navigation/display | Tabs, Separator, Badge, Avatar, Card, Skeleton, Spinner, EmptyState, ErrorState, pagination/load-more controls |
| Layout             | PageContainer, PageHeader, Section, Stack/Grid conventions                                                     |

Use native semantics for straightforward controls. For complex overlay focus/keyboard/positioning behavior, use one established accessible primitive foundation (proposed: Radix primitives behind Rockit wrappers) rather than maintaining another bespoke accessibility framework. Verify browser support, bundle impact, and React 19 compatibility before adoption. Do not mix different overlay libraries per feature. A slider may remain native if it meets the seek/volume requirements.

Radix documents its [focus, keyboard, and ARIA behavior](https://www.radix-ui.com/primitives/docs/overview/accessibility); application composition, labels, contrast, and regression testing remain Rockit's responsibility.

Primitives own appearance, semantics, focus, disabled/loading/error states and reduced motion. They accept layout customization where needed but do not expose unrestricted feature-specific color styling as the normal API. Domain components such as `MediaCard`, `MediaRow`, `Artwork`, `PlayButton`, `LikeButton`, `DownloadStatusBadge`, and `SettingsSection` build on primitives and live outside `ui`.

Replace ContextMenu/PopupMenu/HeaderPopover/dialog duplication with one overlay foundation while retaining the media action registry and domain permissions. Preserve right-click, long-press cancellation on scrolling, submenu behavior, touch action sheets, focus return, Escape, outside dismissal, and drag/drop interaction tests.

Raw-color enforcement covers JSX class strings, CSS modules, inline styles, chart configs, SVG props, and PiP styles. Runtime artwork colors are validated data passed into semantic CSS variables by a shared artwork adapter; fallback/contrast colors come from tokens. Brand SVGs and artwork may contain source asset colors; keep them as centralized assets with a documented narrow exception, rather than treating interface chrome as artwork. Charts use centralized semantic series tokens, not local hex constants.

Add an automated rule/check for literal interface colors and palette utilities outside the token/asset allowance. Add rules for direct native control styling outside `ui`, browser imports in server modules, and runtime imports in server data loaders. Widen lint to all handwritten web source. Remove unused/broken CSS aggregates and duplicate skeleton/checkbox/keyframe definitions after import tracing.

**8. Backend work required for a genuinely fast library**

SSR of the existing full-library response is a useful transition, not the final solution. Make API changes additive so native mobile keeps working while web migrates.

1. Add a bounded library overview contract with counts and small per-kind previews, and a paginated library-items contract accepting media kind, query, sort, limit, and cursor/offset. Specify whether songs include direct membership, songs through album/playlist membership, or both; preserve the existing library song search's nested-collection semantics and deduplication. “All” needs predictable cross-kind ordering, not independently loaded slices that pretend to be globally sorted.
   Proposed additive endpoints are `GET /user/library/overview` (12 previews per kind plus counts) and `GET /user/library/items` (`kind`, `query`, `sort`, `offset`, `limit`; default 50, maximum 100). Return `items`, `offset`, `limit`, `total`, and `hasMore`, following existing collection/search conventions. Reset paging on filter/sort changes and reconcile concurrent membership edits; preserve distinct occurrence identity where duplicates are intentional. These endpoint names and limits are proposed contracts, not existing capabilities.
2. Return stable ordering (including public-ID tie-breakers), ownership/contributor/action metadata, and membership flags required by actions. Avoid issuing one “is in library/is liked” request per card. Return only a bounded page and needed summary fields.
3. Add/reuse small saved-station and playlist-option queries instead of retrieving the whole library. Avoid fetching an entire stats response just for five top albums; reuse home/overview data or a bounded server summary.
4. Preserve and reuse collection `/items` and `/playable` APIs. Viewing one page must not limit “play collection,” shuffle, export, or save-offline to that page. Add a separate library playback resolver if needed to replace the current full-library client expansion, with bounded response/queue handling and cancellation. Bulk operations must distinguish selected IDs from “all matching the filter.”
5. Keep collection cycle/access checks, nested expansion identity, random/repeat behavior, queue paging, and download concurrency budgets. Do not expand every nested collection as part of page rendering.
6. Add stable public user identity to session data if needed for cache/account ownership; `SessionResponse` currently has username but no UUID or locale. A transitional cache key may use the username plus session epoch. Never send the session token to JavaScript as a query key or bootstrap field.
7. Keep backend vocabulary definitions authoritative and add missing keys in every supported language. If a versioned public dictionary cache or build fallback needs a vocabulary revision/export, implement it explicitly.
8. Follow backend layering and regenerate models/HTTP code from the root with `uv run --project apps/backend python -m apps.backend models`. Never hand-edit DTOs or the generated base HTTP implementation. Run backend plus web/mobile/shared checks for contract changes.

**10. Hydration, mutations, and live updates**

For each migrated resource choose one active owner. Static server content uses props and explicit route refresh/revalidation. Interactive server data uses the query cache; it must not also remain in an independent manager atom and local reducer.

- Create a fresh QueryClient for each server request and an account-scoped browser QueryClient lifecycle. Serialize successful DTO data only. Keys include account identity/session epoch plus resource parameters, never credentials.
- Server-prefetch initially visible query data and hydrate with matching keys and timestamps. Configure nonzero `staleTime` and mount/focus behavior deliberately so hydration does not immediately issue the same requests. A background refresh should have an explicit freshness reason, not be an automatic second bootstrap.
- Preserve loaded content while filters/paging refresh when semantically safe; use localized pending indicators and cancellation. Do not briefly show the previous account or a different query's results.
- Reconcile WebSocket events through one bridge. Patch exact cache entries when the event is authoritative; invalidate affected queries for ordering/counts/permission changes. Coalesce bursts. Progress ticks should not refetch a whole page or re-render unrelated screens.
- Define invalidation for likes, library membership, playlists, downloads, metadata/lyrics, pins, social changes, settings, and session changes. Update both visible query-backed views and relevant server views deliberately; a FastAPI mutation does not magically invalidate Next's route cache.
- Server-rendered content also needs a freshness policy when changed from another device: small reactive leaf data where necessary, or a coalesced refresh while that route is visible. Never refresh the whole route on playback-time ticks.
- Use browser mutations for existing FastAPI endpoints, upload progress, and playback actions. Use Server Actions selectively for web-specific cookie/preferences/forms where they simplify the flow; validate and authorize them independently. Server Actions are not a replacement for every typed API method.
- Preserve login cookie behavior across configured frontend/backend origins. RSC fetches cannot propagate `Set-Cookie` to the browser by themselves. Keep working browser auth endpoints initially; if a BFF/auth action is introduced, explicitly forward/reissue cookies with correct domain, path, HttpOnly, Secure, SameSite, expiry, and logout semantics.
- On logout/account switch, abort requests, close sockets, stop/pause relevant playback, clear private in-memory/query/worker snapshots, unmount the old provider tree, and refresh navigation state. Preserve intentionally retained downloaded files only under a defined device/account policy; revoke object URLs and never restore another account's authorization.

**11. Offline and service-worker migration**

Complete this before broadly shipping personalized SSR. Service workers can serve old HTML even when server fetches use `no-store`.

1. Stop generic stale-while-revalidate caching of authenticated documents and RSC navigation/prefetch responses. Preserve Next routing variants and response headers; do not replay one RSC response for a different router tree or locale. Purge/version the old `rockit-pages` cache during worker upgrade and authentication transitions.
2. Cache an explicit generic offline application entry and static assets. It bootstraps validated, account-selected IndexedDB snapshots only in the browser and offers downloaded-media playback. Adapt `/~offline` and its “library” link so it works without another unavailable server navigation. Do not rely on a stale protected route response as an offline permission check.
3. Version stored snapshots, validate loaded data with compatible schemas, and key private snapshots by stable account identity; dictionary keys include locale/revision. Distinguish “backend unavailable while browser online” from actual offline mode.
4. Keep saved audio, covers, playlist/album references, and previously resolved complete playable queues usable offline. A new paginated library cache is not a complete offline catalog: retain an explicit downloaded-media metadata index and migrate existing records before retiring full-library snapshots.
5. Keep range requests and ordinary audio/video responses network-only except explicit download-to-device operations. Retain object URL cleanup, storage quota behavior, iOS persistence requests, and cleanup of old worker/DB versions.
6. Test production worker upgrade, offline reload, direct offline entry, account switching in multiple tabs, logout while requests are in flight, old/new worker clients, and reconnect reconciliation. Development mode currently omits the worker, so dev-only tests cannot validate this feature.

**14. Decisions and practical limits**

- Proceed with App Router/server-first composition, stable session/vocabulary providers, TanStack Query for live API state, and Nanostores only for runtime state where narrow subscriptions help.
- Preserve the proven playback, collection, provider, and offline algorithms while changing dependency ownership and presentation. Rewriting audio algorithms is not needed to fix initial rendering.
- Make backend pagination/summary work part of scope. Frontend SSR alone cannot make an unbounded response cheap.
- Keep initial core content complete; stream or defer slow secondary data deliberately. Do not move every backend request into a blocking root layout or promise literally zero future requests.
- Keep both Stats routes until parity/redirect policy is established. Remove only verified dead code; preserve existing user-facing functionality unless a deliberate replacement is specified.
- No deployment platform migration, new auth provider, backend rewrite, or wholesale native UI rewrite is implied. Shared API/runtime changes include native compatibility verification.
